# ROADMAP.md: what's still to do

The road map for perfecting this MCP. When an item is done, check it (`[x]` in the Done column)
and document the result as `.claude/rules/docs.md` describes; checked items can be deleted later (git history keeps
the record). A checked item's figures (sizes, counts, times) are those of when it was checked, and aren't updated
after. Effort is a rough guess: S = under an hour, M = a few hours, L = a day or more.

Numbers are stable IDs (other docs cite them); within a section, the order of the rows is the
priority. Items should come from real use (item 31) more than from reviewing the project itself. A branch proposes an
item only for work it can't take on itself, as the `delegate` skill's What looks like a ROADMAP proposal says
(`.claude/skills/delegate/SKILL.md`).

**Faster test runs:** the live self-test runs each category in a Designer of its own, several at once
(`tests/test_all_tools/workers.py`), which took a full pass from about 12 minutes to about 3.4 (2026-11-10).
`workers.py`'s docstring gives the latest time of a full pass. Items here that this work found say so.

**Fewer tools.** The server went from 43 tools to 35 by turning the single-edit tools into `apply_edits`
ops (fewer choices make the right one easier to pick, and the tool list costs every session tokens).
A new capability is first a parameter or an op of an existing tool; a new tool when it doesn't fit, such as a
workflow of its own (item 33), rather than complicating an existing tool with completely different logic. The items
below are written that way.

## 3D view

Judging a material in Designer's own renderer, on what item 7 built (`screenshot_designer('3d', ...)`, `designer_helpers/view3d.py`).

An item here that changes what the 3D view shows is built from the start into the set-up (`_3d_set_up`,
`designer_helpers/scene3d.py`), as the camera, the mesh, the tiling, the light and the shader model are, so its shots
settle and its change is put back as theirs are. A value the 3D view's state file holds is a field of the file
(`StateField`, `designer_helpers/state3d.py`), written in the call's loads (item 131; `scene3d.py`, step 4). A value the file doesn't
hold is a step of its own, through the view's menus or toolbar:

- **Checked first:** the step's menu entries and buttons are looked up, and refused, before anything changes
  (REVIEW.md HLP-127). A field of the file can be read only once the set-up's Save has written the file: a file
  lacking the field is refused then, before the view changes (`_state_fields`). One exception: a field of the material
  of a mesh file the call loads is refused only once that file has loaded, as its materials are known then (item 84;
  the lead, 2026-11-27).
- **Per material:** a field of the material the mesh uses, as the tiling and the shader model are, goes in
  `PER_MATERIAL` (`state3d.py`): its place is found by that material's id (`_used_material`), for a mesh file among the
  materials the Materials menu lists in use (REVIEW.md HLP-322). It is refused for a mesh using several materials before
  anything changes (`view3d._material_checked`, `MATERIALS_USED`), but for a mesh file the call loads, once loaded
  (Checked first, above). It is written with that material held overridden, as it shows only with Override Material on:
  one the user had off is turned on for the render and said, the field named as `OWN_SAID` names it (`scene3d.py`, step
  4; REVIEW.md HLP-316, HLP-321).
- **Skipped when shown already:** a field the user's state holds already isn't written, and with nothing to write
  nothing is loaded (`_state_changes`; REVIEW.md HLP-195), but a tiling or a shader model on a material whose Override
  Material is off, which the set-up turns on (`scene3d.py`, step 4). A step's value the view shows already, such as a
  checked action, isn't set again, and costs no wait. A toggle already on isn't triggered, which would turn it off.
- **Waited for:** the load waits for its end, then for the view at rest once the camera's glide is over
  (`_state_load`). A step goes in `with _Waiting(watched)` (`designer_helpers/frames3d.py`). Either is the view's
  wait, never a time.
- **Counted as a change:** the set-up's `may_change` includes the new option, so a 3D shot takes a render before it.
  The set-up returns whether it changed the view, so an identical render after it is taken again, then said (`STALE`,
  `designer_helpers/shot3d.py`).
- **Said as it goes:** `3D view, setting: ...` is printed before the change. The change is recorded once made, before
  its wait, so an error after it says what was set (REVIEW.md HLP-200).
- **Said as text:** the value gets a line in the 3D view as text (`_shown_said` in `designer_helpers/scene3d.py`; a
  field of the file, `_field_said` in `state3d.py`), or is listed in item 85's Not said.

## Ideas, not yet decided

Add ideas here before they are prioritised into a table above.

- **The function-graph table on bool and string parameters:** GUIDE.md's table is measured on float4 and enum parameters and `$` ones; nothing says these differ, and nothing has measured them.
- **A `duplicate` op:** the API has no call for it, so it means copying a node's values, `$` inheritance and function graphs by hand. The other MCP's `duplicate_node` copies none of them and refuses library nodes. Only if real use (item 31) keeps needing it.
- **Deleting a graph:** no tool does it. `SDResource.delete()` is in the API (read from Designer 16's file, not run). Destructive, so it would want the same care as item 15, and it may belong with it.
- **Starter node chains for materials:** the other MCP's 79 recipes build whole materials in one call. Only their wiring was checked ("0 port failures, 0 crashes"), not how they look, and they say they come from one professional's 512-node graph, so write our own rather than copying them, and only if item 31 shows agents keep rebuilding the same chains. Designer's own `materials/pbr/...` are already a starting point.
- **The 3D Viewer node** (Filter > Effect): it ray-marches a scene of function graphs (SDF or intersections) with a camera and an environment of its own, computed like any node, so no UI and no clipboard. A material would need a scene built for it, its maps sampled from only two image inputs. Only if the 3D view's set-up (item 7) proves fragile.
- **Wrong value types in a script:** the other MCP reports that `SDValueInt2` on a float parameter and `SDValueFloat` on an enum silently crash Designer 15. The `set` op converts by the parameter's type, so this reaches only a user's own code. Unmeasured on 16; if measured, only in a Designer the self-test started, since it may crash.
