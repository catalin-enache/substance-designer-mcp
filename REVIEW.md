# REVIEW.md: review findings

Findings from code reviews of this repository, kept across several reviews as a file in the project. How many is
the user's choice, most likely the life of a feature branch; the history stays in git for good.

This file is the **memory per branch**. Agents that review and agents that address findings talk through it, as
in a PR review: a finding is raised, then fixed or answered with why not, so the next reviewers know what was
settled and don't raise it again. Once the branch is merged it can be cleaned up. `DECISIONS.md` is the memory for
the whole project.

A new review **appends** its findings to the matching severity section and adds itself to the log; it never removes
or rewrites existing entries. An entry is checked when it is resolved, always with a resolution line that starts
with one of these wordings: done, not a bug, not reproducible, won't fix. Format and rules:
`.claude/skills/project-code-review/` (SKILL.md, TEMPLATE.md).

**Confidence.**

- *Confirmed*: the lead agent read the code and the defect is visible in it, as quoted.
- *Measured*: reading couldn't settle it, and the lead agent's scratch probe in Designer showed it (the entry gives
  the probe and what it measured; the `project-code-review` skill). A finding is one or the other, never a guess.

**IDs.** One prefix per area, numbered on: **PLG** plugin and bridge protocol, **SRV**
`mcp_server/server.py` and `server_tools/`, **HLP** `mcp_server/designer_helpers/`, **INS** installer, uninstaller,
command-line client and example, **TST** tests and docs. A new area gets a new prefix, added here.

**Last used:** PLG-33, SRV-100, HLP-82, INS-27, TST-202.

A new finding takes the next number for its area, and whoever writes it updates this line in the same edit. Only a
new finding raises it, and a cleanup leaves it as it is. Nothing lowers a committed number; dropping a finding before
committing it undoes its change.

**Findings no longer here.** Only the user starts a cleanup of this file (the `cleanup-review` skill). An ID
cited elsewhere but missing here was usually removed by one, which isn't a dangling reference.
`python3 scripts/review_lookup.py HLP-56` prints the whole entry, from this file or its git history, from any folder
of the repo. If it can't, it says why: the ID never existed, a squash lost it, or the clone is shallow.

- [x] **SRV-82 · A listener on another port can relay the client's login to the real plugin and run its own code** · `mcp_server/server_tools/core.py:162-173` · confirmed · found 2026-11-07
  - **Defect.** The client's answer is `HMAC(token, nonce)` alone (`auth = hmac.new(token..., nonce..., sha256)`), and the plugin checks only that (`compare_digest(req['auth'], expected_auth(self.token, nonce))`), so the answer isn't tied to the request it came with. Before this branch the tools only reached `PORT`, where a squatter kept the real plugin off the port; now `port=` makes them connect to any port while a real plugin listens on another.
  - **Scenario.** Another local account listens on 9902 (or on a port an agent's Designer just left after `quit_designer(port=...)`). An agent calls `designer_status(port=9902)`. The listener connects to the real plugin on 9877, passes its nonce on as its own greeting, receives our HMAC and sends its own `code` with it to 9877: code running in Designer as the user. This isn't the plugin authenticating itself (DECISIONS.md, "Only the client is authenticated, not the plugin": its reasoning has a fake plugin learn only the script; its Reopen if doesn't literally hold), so it is reported for the user to weigh.
  - **Fix.** Bind the answer to the request: sign the nonce together with a hash of the request body (a protocol change in the plugin, the server, `client/sd_run.py` and the self-test's `raw_request`, together). Or keep `port=` to ports this server recorded or launched.
  - **Resolution: done**. The user chose binding the answer (DECISIONS.md, "A client's answer is bound to the port and the request; `port=` takes any port").
    - **Test:** `tests/unit/test_plugin.py::test_an_answer_relayed_from_another_port_is_refused` (the server and `sd_run.py`, the request passed on as sent and with its code swapped, through a relay to the real plugin code): all four ran (`'output': 'MINE\n'`, `'RELAYED\n'`) instead of `invalid token`. `test_clients_send_nothing_to_a_plugin_of_another_protocol`: both clients answered a greeting without a protocol. Live, `bridge.check_a_relayed_answer_is_refused` (`designer_status(port=<relay>)`, the relay sending `print('RELAYED')` with the server's answer), in its scratch run: `[{'ok': True, 'output': 'RELAYED\n', 'error': ''}]`; after the fix, `invalid token`, with `check_bridge_security` passing (`v4`).
    - **Cause:** the answer was `HMAC(token, nonce)`, which says nothing about where it was sent or what it authorises, so whoever got it could use it with the real plugin for any request while the nonce was fresh.
    - **Fix:** the answer is now an HMAC over the canonical JSON of the nonce, the port the client connected to and the request without `auth` (plugin docstring); the plugin checks it against its own bound port and the request it parsed (`expected_auth`, `_authorised`), so a relayed answer fails on the port, and a swapped request on the request. The greeting names the protocol (`PROTOCOL = 2`, plugin `VERSION` 4), and the server (`bridge_answer`, `_exchange`) and `sd_run.py` send nothing to a greeting of another one: an older plugin would accept the old answer, which is what a relay needs. `BRIDGE_PROTOCOL` lives in `project_constants.py` (`test_the_clients_know_the_plugins_protocol` checks the plugin's matches). `alone.close` now asks `quit_designer` when `designer_status` fails, so a Designer an agent started on the older plugin is still ended after an upgrade (`test_close_asks_quit_designer_when_the_status_fails`; seen live: "forced: it had not closed"). README (Security, Troubleshooting, `v4`), AGENTS.md (The bridge protocol).
    - Note (2026-11-07): the canonical JSON this signed was replaced by the request's bytes as sent (PLG-32).
    - Note (2026-11-07): the clients' protocol check isn't what keeps a relay from an older plugin, as the Fix line says: the new clients never compute an older protocol's answer, so any other plugin refuses it either way, and a program can claim protocol 2 in its greeting. The check sends nothing to a plugin that would refuse it, with a clear error (TST-166).
    - **Also covered:** every client of the protocol (searched `nonce`, `hmac`): the server, `sd_run.py` and the self-test's `raw_request` all sign the new way; `test_every_client_speaks_the_plugins_protocol` runs all three against the real plugin code, with non-ASCII code and a fractional timeout, since both sides sign their own serialisation of the request. Not covered: the signature doesn't make the plugin prove itself (DECISIONS.md, "Only the client is authenticated, not the plugin"), so a program on a port a tool is pointed at still receives that request's script and can send a made-up reply.
  - Questioned by TST-190 (2026-11-07).

The `agent_designer_file` docstring ("servers launching Designers at the same time never write the same one") holds only for different ports.
  - **Scenario.** (a) Two sessions launch on 9877 at once: the first Designer is left unrecorded, so `quit_designer` refuses it and `_users_next_to` refuses launches on other ports because of it. (b) PLAN.md step 2's workers launching together: one server's `_agents()` reads another's record between truncate and write, gets a `ValueError` and unlinks it. (c) A failing `pgrep` deletes a live record.
